④ 模块职责与文件对应

📡 protocol.rs — 线协议层

  • Request 枚举: Publish / Subscribe / QueryEndOffset
  • Response 枚举: Published / Message / EndOffset / Error
  • NDJSON 成帧: 每条消息 = 一行 JSON + \n
  • write_request / read_request — 序列化/反序列化

🏢 broker.rs — 服务端

  • State — 全局共享状态 (topics HashMap)
  • TopicLog — 每个 topic 的日志 + 订阅者列表
  • spawn_broker() — 启动 accept 循环
  • publish() — 追加日志 + 锁外扇出
  • run_consumer() — 注册 + 重放 + 实时跟随

🔌 client.rs — 客户端

  • Producer — reader + writer，同步 publish → 等 offset 确认
  • Consumer — writer 发订阅请求，reader 持续 recv 消息
  • try_clone() 分离读写，避免 BufReader 缓冲冲突

🔑 并发设计要点

  • thread-per-connection: 每连接一个线程
  • Mutex 临界区极短: 锁内操作数据，锁外做 I/O
  • crossbeam channel: 有界缓冲 (1024)，提供背压
  • 原子注册: 订阅注册 + 历史快照在同一次锁内完成

⑤ 为什么 Producer/Consumer 都需要 reader + writer？

  // TCP 全双工: 连接两端可以同时收发

  Producer 的视角:
  ┌──────────────────────────────────────────────────────────┐
  │  writer ──write──▶ Publish{topic, payload}    发请求给 broker  │
  │  reader ◀──read──  Published{offset}             读 broker 的确认  │
  │                                                          │
  │  Q: 为什么不只 write？                                       │
  │  A: 需要知道消息被分配的 offset（同步确认，类似 Kafka acks=all）│
  └──────────────────────────────────────────────────────────┘

  Consumer 的视角:
  ┌──────────────────────────────────────────────────────────┐
  │  writer ──write──▶ Subscribe{topic, from_offset}  发一次订阅请求   │
  │  reader ◀──read──  Message{...} (持续)          持续收推送消息     │
  │                                                          │
  │  Q: 为什么不只 read？                                        │
  │  A: ① 必须先发 Subscribe 请求告诉 broker 从哪开始           │
  │     ② writer 持有 TcpStream，drop 会关闭连接               │
  └──────────────────────────────────────────────────────────┘
